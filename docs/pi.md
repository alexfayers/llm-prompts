# Pi

`llm-prompts install pi` writes everything under `$PI_CODING_AGENT_DIR` where that is set, otherwise `~/.pi/agent`.

## What gets installed

- Rules go into the global `AGENTS.md`, and one file each under `rules/` for agent definitions (see [Roles](#roles)).
- `AGENTS.delegate.md` next to it holds the same rules without the ones whose frontmatter sets `audience: main`. Those rules only apply to the session that talks to the user. Any other `audience` value fails the install.
- [cline-hooks](https://github.com/alexfayers/cline-hooks) is wired in as a pi extension.
- Pi packages listed in `prompts/pi/settings.json`, from core and overlays, are merged into `settings.json` in the agent dir. Pi installs them on startup. Packages you add yourself are left alone. A package can be an object with a `source` and `load_when` conditions, only `env:` and `tool:`, and is added only where they hold at install time.
- `mcp-memory install pi` registers the memory servers in `mcp.json`, which pi's MCP support reads.
- The `CommitGuard` hook blocks a git commit or push until the repository's test command passed on the current files. It also replaces a test run by itself with an `echo` while the same command, with the same arguments and in the same directory, last passed on the same files and tool versions: `uv` for `uv.lock`, `pnpm` and `node` for `pnpm-lock.yaml`, `npm` and `node` for `package-lock.json`, `cargo` and `rustc` for `Cargo.lock`. A tool whose `--version` fails or takes over 5 seconds never lets a run be skipped. A run counts with a prefix such as `cd <dir> &&` or `timeout`, or redirected to a file. It doesn't count when piped, or when anything follows it except `&& echo`, `printf`, `true`, `pwd`, `ls` or `cat` writing to no file except /dev/null. It also blocks a push while the tree has uncommitted changes. The test command is `PI_CONTEXT_TEST_CMD`, or else the one `shared/test-gates.json` detects from the repository's files, with each overlay's gates checked first. A gate gives the exact `command`, or a `pattern`: one regex or a list of regexes that must match the whole run, its words shell-quoted and joined by single spaces (`tool --name 'a b'`).
- The `PrimaryCheckoutGuard` hook, in every frontend, blocks an agent command that changes a repository's primary checkout (commit, reset, rebase, a merge or pull without `--ff-only`, push, `gh pr create` and similar), so work happens in a worktree. The exact same command again proceeds.
- The `ShellRules` hook removes `-e` from `set` calls and runs the corrected command with a note. It blocks `set -o errexit`, a `set -e` followed only by words that may expand to nothing, killing processes by port and Docker volume removal.
- The `ReviewLimitGuard` hook blocks `gh pr create`, and review commands other plugins add through `open_reviews()`, at the limit under `[reviews]` in `config.toml`, 5 by default. The limit is best effort, so parallel creates can go over it by a few.
- Files under `prompts/pi/seed/` are copied into the agent dir only where absent, so they stay yours to edit. A later overlay replaces the same path. For an existing JSON file, seed keys it has never been offered are added once.

## Roles

Each rule is also its own file under `rules/`, and the global `AGENTS.md` holds only the rules for the ordinary lead.

- A rule without `roles` frontmatter, or with `roles: all`, is core and reaches the lead and every agent.
- `roles` can list any of `lead`, `coordinator`, `reasoner`, `worker`, `surveyor`, `reviewer` to limit a rule to those roles. Only Pi reads it. An invalid value fails the install.
- `load_when: <condition>` on a rule with no roles or only `roles: lead` leaves one condition to the session, and keeps the rule out of the lead and every definition. Only Pi checks it in the session. A condition is `env:<NAME>` (the variable is set and not empty) or `tool:<name>` (pi has the tool, or the command is on PATH). It can be combined with `roles: lead` and `audience: main`, which keeps the rule out of cold workers (a `PI_CONTEXT_CHILD` handshake without `inherited`). Any other condition is listed under its own name for another extension to check. With several conditions, the install decides the `env:` and `tool:` ones and leaves the one other condition to the session. A rule left with no session condition, because its conditions are all `env:` or `tool:` and it has several of them or other roles, is decided at install time and goes into `AGENTS.md` and the definitions by its roles, as usual. `load_when` cannot be combined with `paths`, and `audience` cannot be combined with `paths`. Every install checks these keys, for every agent.
- A core or lead rule with `paths: <glob list>` stays out of the lead `AGENTS.md`. Role definitions still get it for their roles.
- The install lists `load_when` rules by condition, and `paths` rules by `paths:<glob>`, in `conditional-rules.json` in the agent dir. The `load-when` extension adds each rule's text from `rules/` to the lead session and fork delegates when its condition holds, or once a `read`, `grep`, `find`, `edit` or `write` call touches a file matching one of its globs, relative to the working directory.
- Each generated agent definition starts with one `@../rules/<name>.md` line per rule for its role, and sets `inheritGlobalContext: false`.
- A definition's role is its source's `name`. A source with `rules` gets only those rules, one with `omitClaudeMd: true` gets none, and any other name gets every rule except the rules that leave a condition to the session.
- Roles are fixed when an agent starts, so changes apply to new agents.

`llm-prompts check` measures the expanded text of each definition and of the lead as `pi_role_prompt_bytes`. The `collection_bytes` total counts the global `AGENTS.md` and the rule files, not the agent definitions or their expansions.

## Fork usage accounting

Full fork snapshots stay byte-for-byte in `<agent dir>/pi-context/kept/`. Usage tools read only child entries from `<agent dir>/sessions/pi-context/`. If retention fails, the full run files remain without an expiry marker and the delegate's reply is preserved.

Preview historical repairs with a Node version that runs TypeScript files:

```bash
node ~/.pi/agent/extensions/pi-context/usage-sessions.ts --agent-dir ~/.pi/agent
```

Add `--apply` to archive the original files and replace their accounting copies. Forks can keep running.
Before `--apply`, exit or `/reload` every lead that runs an older `pi-context` once its delegates finish cleanup, so it cannot start new forks.
The migration streams parent signatures and processes one retained snapshot at a time.
It leaves unrelated sessions and files that change during the run alone, and stops on uncertain ancestry, unreadable related parents or missing archives.
Inherited entries without usage may differ from the parent in content only. A retained file identical to the start of a parent keeps no usage.

The call returns at once and the delegate keeps running. The full reply is available through `result_fetch`. `role: "writer"` runs a `writer` delegate in a git worktree under `<agent dir>/pi-context/worktrees` on branch `fork/<name>`. Another extension can register a worktree provider on `globalThis[Symbol.for("pi-context.worktree-provider")]` that makes and removes that checkout instead, and a writer whose `target` is not a git checkout writes in place there and lands nothing. When it replies, its commits land when they sit on the main checkout's current branch tip, or on the commit where that tip left `origin/main` with every commit of that tip that `origin/main` lacks (matched by patch or subject), hold no `fixup!`, `squash!` or `amend!` commit and name no private path (the home directory, or a match of the `llmPrompts.forks.privateNames` setting), and the main checkout did not change: the main checkout fast-forwards to them and the worktree is removed. Otherwise the landing escalates to the lead with the reason and keeps the worktree. With `branch` (and optionally `base`, a ref, default the current branch) a writer starts on that new branch from the base instead, pushes it with `git push`, and the landing is that push: unpushed commits escalate and nothing lands on the current branch. One landing runs at a time per main checkout and nothing is pushed. `target` names another directory, git checkout or worktree, with `~` and paths relative to the session directory allowed: a reader runs there, and a writer branches from it, lands on its current branch and may not name it, so give each branch its own writer. With `model` the delegate is a cold worker: a fresh session on that model (`provider/id`, optionally `:thinking`) with only the role's skills, the role card appended to its system prompt, `AGENTS.delegate.md` in place of the agent dir's `AGENTS.md`, and no MCP servers of its own. It reaches only the role's MCP tools, through the same socket as the MCP proxy, which is always on for a worker. A cold writer starts in its worktree. It uses the same landing queue. A new cold worker whose model, role and directory match a cold worker still on its first request waits up to 60 seconds for that request to end before it sends its own prompt, so it reads that prompt cache instead of writing the same one again. The widget shows `waiting for cache` while it waits. A fork without `model` or `from` whose session holds more than 150000 tokens of context starts as a cold worker on the model and thinking level of the session, and its task starts with a summary of the session that the model writes. A background run's result reaches the session as a `pi-context-results` message that starts a turn as soon as the run ends, or is added when a busy run settles. Each `ASK:` line of the result is pinned as the pending ask `fork-<name>-<run id>-<n>`, and the message names the pins. The pins clear when the main run that got the message settles, unless it was aborted or an `ask_user` call in it was cancelled, timed out or failed. They also clear when `fork_resume` or `fork_steer` names the fork. In a session without a UI (`pi -p`) the session does not finish while a background run is live, for two hours at most. A tool result of main also names each background run that has run `llmPrompts.forks.checkInMinutes` minutes (default 5, `0` turns it off) since it started or was last named, with its turns and last tool call, unless an `llm-prompts watch` call of it is still running. While a background run is live, a widget above the editor shows each one's name, role, elapsed time, turns, `target` when it is not the session directory, `from <name>` when it shares the prompt cache of a fork it started from (`from <name>#<key>`, with the start of the cache key, when two shown sources have that name), and latest tool call or text. Finished background runs whose result main has not received yet share one widget row of counts per outcome, such as `✓ 3 done · 1 blocked · cache 2-5m left`, and a run comes back to that row when an aborted or failed main run re-announces its result. A finished run with an open ask keeps its own row until the ask is resolved. Each `ASK:` line of a fork's reply is pinned as a pending ask. `fork_cancel` stops a background run by name, and `fork_steer` sends a live one a message that reaches it before its next model call. The runs are saved in the session with any result main has not read yet, so a session resumed after a quit delivers it, and a run that was live when the session ended comes back as lost, naming a reload that ended it and its kept worktree. A writer that ends without landing and leaves its worktree clean, with no commits, loses the worktree and its branch, and `fork_resume` makes them again. A lost run keeps its session file, and `fork_resume <name>` continues it in the background in the same worktree with the same role, model and run id. Only the top-level session can fork. A delegate's environment names its role (`PI_CONTEXT_ROLE`) and its run (`PI_CONTEXT_RUN_ID`). A finished fork (done, found-it, blocked or failed) keeps its session files for 24 hours after it ends. Every complete session snapshot is archived by its content hash under `<agent dir>/pi-context/kept/` and never removed. `<agent dir>/sessions/pi-context/<name>-<run id>.jsonl` contains only the delegate's entries for usage accounting, without inherited history. Then `fork_resume` with a `task` gives it that new task in the background on its own session, model and role. `fork_steer` on a finished fork gives it the message as that task. A reader works in its old directory or `target`. A writer works in its kept worktree, or else a new one from the current branch of its checkout. When a finished fork of the same role and directory still has a warm cache, the `fork` result adds a line naming it and its context size. Where `systemd-run --user --scope` works, each fork process, and every process it starts, runs in a scope capped by `memoryMax` and `cpuQuota` under `llmPrompts.forks` in pi's settings (systemd values such as `16G` and `400%`), by default a quarter of the host's memory and half its cores. Elsewhere forks start uncapped and pi-context logs that once. At most `max_live` forks under `[forks]` in `config.toml` (default 10) run at once. `llm-prompts install` copies the limit to `pi-context/forks.json` in the agent dir. A fork over the limit waits in a queue and starts when a running one ends, and its `fork` call says `queued`. `fork_resume` starts a queued fork that a reload dropped. `shared` with `tasks` and `model` runs one cold stub that reads the `shared` text and the contents of each file in `sharedFiles` (paths relative to the session directory or `target`, read through the `read` tool so its permission rules apply, each at most 100000 characters, and put into the stub's prompt) in a single request with no read turns. When the stub finishes, one child per task continues a copy of its session, so the children read the stub's prompt cache. Up to 2 children start over the limit and the rest queue. With `mcpProxy: true` under `llmPrompts.forks` in pi's settings a fork starts with `--no-mcp` and runs its MCP calls in the top-level session over a private socket, so no MCP server is started twice. The fork gets proxy tools with the same names, namespaces and exposure, the same active tools and the same `mcp_servers` prompt section. In the top-level session, `/ghost save <name> [param=value ...]` saves the tool calls of the last run as a ghost under `<agent dir>/ghosts/<repo key>/`, `/ghost list` lists this repository's ghosts, and the `ghost_run` tool replays one without a model call per step, stopping at the first step whose result differs. |
