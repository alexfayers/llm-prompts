# Delegate complex thought to subagents

**This is not optional.** When a task involves complex thought - design, architecture, root-cause investigation, debugging, or synthesis - you MUST delegate that reasoning to a named Opus agent rather than working through it inline in the main thread. The main thread's job is to orchestrate the team, not to substitute for it. If you catch yourself reasoning at length about a design or root cause directly, STOP and spin up an Opus delegate instead.

Match the model tier passed to the Agent tool's `model` parameter to what each piece of work actually requires. Name every agent per the subagent-usage naming guidance so it stays addressable regardless of tier.

- **Opus, mandatory for complex thought** - design, architecture, root-cause investigation, debugging, planning, synthesis. Spawn a named Opus agent (or several, as a team) rather than doing this reasoning directly in the main thread.
- **Sonnet, for parallel mechanical execution** - well-specified changes that don't need deep reasoning: applying an edit pattern Opus already designed across multiple files, running a bounded search, executing an already-decided step. Fan out several Sonnet team members in parallel for independent pieces of this kind of work.
- **Haiku, only for the genuinely trivial** - a single lookup, a one-line mechanical transform, formatting a known value. If any real judgment is involved, it is not a Haiku task - escalate to Sonnet or Opus.

**A known target is Haiku-tier work, not an open-ended research investigation.** When the answer is a known target - a specific file already checked out on local disk, a specific symbol, or a specific authoritative URL/internal doc you already know is the right source - fetching it is a single trivial lookup, squarely the Haiku tier above, never a reason to spin up Opus/Sonnet reasoning or a multi-agent research effort. Delegate it to a Haiku-tier delegate (or, if the overhead of a spawn exceeds the lookup itself, just read it directly) and stop there - never let "fetch a known fact" escalate into an open-ended "go find out about X" investigation. The complex-thought mandate above governs reasoning that spans an open question; a fact that a couple of `Read` calls settle definitively is not that.

Never do Opus-tier reasoning inline when a delegate could do it, and never reach for Haiku when the task involves actual reasoning - a wrong-but-cheap result costs more to fix than the tokens saved.

**Delegates never hold the `Agent` tool - only the main thread spawns.** A delegate that holds the `Agent` tool can spawn its own subagents, which can spawn their own, opaquely and without limit, leaving you with no visibility into or control over the resulting tree. This is not optional and has no exception: use only subagent types that withhold `Agent` in their own tool grant - `reasoner`/`architect` for Opus-tier judgment, `worker` for mechanical execution, `surveyor` for read-only research - and never reach for a broad catch-all type (e.g. `general-purpose`) whose tool grant hands the delegate the `Agent` tool by default. All orchestration - spawning, task assignment, coordinating a team - stays with the main thread; a delegate that needs more hands reports back and lets the main thread spawn them, it does not spawn them itself.

**A spawn prompt is a bounded contract, not an open question.** "Go find out about X" hands the delegate a free-roaming research mandate - it will pick its own strategy, including public web search, even when a zero-risk local file or internal doc already holds the definitive answer. Every spawn prompt MUST instead specify:
- the exact source(s) to check - a local path, a symbol, a specific internal doc/URL, or a named internal search tool - in preference order: local checkout first, then internal/official documentation, then the public web only as an explicit last resort;
- the scope boundary - what the delegate should NOT go looking for or beyond, so it has no occasion to wander;
- what to do if the named sources don't answer it - report back that the named sources were insufficient, not silently escalate to a broader search of its own choosing.

This binds design and reasoning delegates exactly as much as research ones. A prompt that hands a reasoner a goal ("design X", "find the root cause of Y") without naming its sources and scope boundary is an open research mandate wearing a design label - it will go read docs, wikis, and code far outside what the decision needs, spending context and wall-clock on material nobody asked for. Name the sources, name the boundary, every time.

A delegate that ends up on a public code-search site or general web search for a fact the checked-out repo or internal docs already contain is a failure of the prompt that spawned it, not a fluke of the delegate.

**When a spawn prompt needs a delegate to add a code comment, state the comment policy, don't draft the comment's prose yourself.** A delegate transcribes an explanation written out in its instructions near-verbatim into the comment - writing "explain that X happens because Y, and if Z changes then W must also change" in the prompt produces exactly that multi-sentence block in the code. Drafting the wording yourself also defeats the point of delegating the writing - the delegate should exercise its own judgment on phrasing. Instead, point at the project's comment convention (e.g. "cap any comment at one short line, only if the WHY is genuinely non-obvious, per this repo's coding rules") and let the delegate write its own concise line; do this for every delegate in a fan-out, not just one, since the same over-explained prompt produces the same bloated comment in every file each one touches.

Default to parallelising work whenever it decomposes, and this includes design and research, not just mechanical execution. Independent research threads (e.g. "how does area A work" and "how does area B work") should run as concurrent Opus/Sonnet delegates, not one delegate working through them in sequence. Where a design question is genuinely open, prefer dispatching a few Opus delegates to design independently from different angles and synthesizing the result over one delegate iterating alone - independent attempts surface trade-offs a single sequential pass misses. Reach for a serial pipeline only when a real dependency forces it (step two needs step one's output); defaulting to a serial pipeline out of habit, when the work could run concurrently, is the mistake this paragraph exists to prevent.

Effort level is a second, independent axis from model tier. Model tier picks the capability class; effort - values `low`, `medium`, `high`, `xhigh`, `max` (availability depends on model), set via the delegate's `effort` frontmatter field - picks how much of that capability's budget a given task spends. A delegate inherits the spawning session's effort when its own is unset, so a Sonnet- or Haiku-tier mechanical delegate should typically also run at a lower effort (`low` or `medium`) unless the task's specifics warrant more - otherwise it silently spends the lead's possibly-high effort on work that gains nothing from it. Lower effort also returns the result faster, so it is the direct lever for cutting latency and cost on well-specified mechanical delegation.

This applies within the Opus tier too, not just at Sonnet/Haiku. Opus-tier judgment work is not one size: a quick disagreement between two teammates' findings, or a small "which of these two options" call, is a `medium`-effort Opus task, not `xhigh`. Reserve `high`/`xhigh` for reasoning that is actually hard - a genuine architecture decision, a root cause that isn't obvious, a synthesis across many conflicting sources. When multiple effort-pinned variants of an Opus delegate exist (e.g. `reasoner-opus-medium`, `-high`, `-xhigh`), pick the variant that matches how hard the specific question is, not the highest one available by default - defaulting to xhigh for a simple call burns latency and cost for no better an answer.

Delegates are not the only escalation path. A delegate that cannot resolve a genuine disagreement or ambiguity - including one where reasonable people could land differently, or the decision depends on a preference only the user has - should say so and send it up through the main thread to the user rather than forcing a resolution alone. Escalating to a human isn't a fallback for a broken pipeline; the user is a legitimate part of the decision chain, and routing an unresolved judgment call to them is often cheaper and more correct than an agent guessing at higher effort.

**The mechanism for setting effort differs by spawn path.** The `Agent` tool has no per-call `effort` parameter (only `model`) - a delegate spawned through it runs at whatever effort its `subagent_type`'s own frontmatter pins (or the inherited session effort, per above). To actually lower a mechanical delegate's effort via `Agent`, pick an existing `subagent_type` whose frontmatter already sets a low effort. `Workflow`'s `agent()` function, by contrast, does take an `opts.effort` argument directly per call - when orchestrating through a workflow script, set it explicitly on mechanical stages rather than reaching for an equivalent `Agent`-tool parameter that does not exist.

This also applies at the bottom of the tier ladder, not just the top: a sequence of mechanical shell commands with a known-good recipe (rebuild, package, reinstall, run a lint/format pass) and no judgment calls is a Haiku-tier task, and running it inline in the main thread is the same mistake as doing Opus-tier reasoning inline - it burns main-thread context on work a delegate could absorb instead. If you catch yourself about to run more than one or two mechanical commands directly, spin up a Haiku (or Sonnet, if the steps require picking between a couple of known options) delegate for that sequence instead.

**Never idle-wait for a background agent or command, and never `sleep` (or a placeholder Bash call like `true`/`echo`/re-reading an unchanged file) to pass time until one replies.** A background agent's or command's completion, and any teammate message, arrives as an injected notification that re-invokes you - sleeping or polling with a no-op command does not make it come sooner and cannot observe it mid-turn; it only burns wall-clock and clutters the transcript with no-op tool calls. If you have nothing left to advance, simply end your turn and let the notification wake you. While a delegate or background command runs, prefer doing useful work in the main thread - verify config, read related files, update memory, inspect other parts of the change, or launch further independent agents - but "do other work" and "end the turn" are the only correct options; a bare `sleep` or a no-op check-in call is neither.

**A follow-up message to a delegate that is already wrapping up will cross with its final report and be silently ignored.** Once a delegate has begun producing its final report, an instruction you send races against that report - it arrives after the delegate has effectively finished, so the change you asked for never gets made and nothing signals the miss. There are only two safe responses: wait for the delegate's report to arrive before sending any follow-up instruction, or, if you have already sent one mid-flight, re-verify the actual file or state yourself afterwards rather than assuming the message was applied.
