# Local before remote

- Before running any search, MUST check whether the answer is already visible in the current context. A skill's own preamble (e.g. a "Base directory for this skill: ..." header), a prior tool result from the same turn, or a path or value stated in the instructions you are following is not a lookup target - it is the answer. Check this first: before memory, before a known-target lookup, before anything else.
- Before searching for anything you do not already know, MUST search project and global memory (per `memory.md`) for this exact question - a prior session may have answered it, including one where the user said exactly where to look.
- Where memory has nothing and the answer is a known target, resolve it directly; no need to ask. A known target (per `delegation.md`) is a specific file you already know is relevant, a tool's own `--help`/`man` page, a symbol in the current codebase, or a doc or URL you already know is authoritative. These are cheap, bounded lookups.
- Where memory has nothing and the answer is NOT a known target, MUST ask the user where to look before searching anywhere else. MUST NOT guess by launching a broad local search (`find` across unrelated directories, grepping the whole filesystem, walking directories you have no reason to think are relevant), and MUST NOT reach for public web search either - both are the same mistake aimed at different targets. The user often knows the best source (an internal tool, a specific doc, a team convention) that a blind search would never surface, and asking costs one turn against the many an unguided search spends.
- MUST persist the answer to memory once resolved - whether it came from the user's pointer or a bounded direct check - so the question is answered from memory next time instead of asked or searched for again. Follow `memory.md`'s entity and observation conventions.
- Memory can be stale, so treat what it says as a strong prior rather than a verified fact, especially for factual content. A `user-preferences` entity rarely changes and can generally be trusted as-is; a `pattern` or `knowledge` entity pointing at a source of information (a file path, an API, a tool's behavior, a config value) records only what was true when it was written.
- Where the cost of being wrong is non-trivial - an action you are about to take, a claim you are about to state as fact - MUST verify the memory-recorded source before relying on it. A small Haiku-tier delegate (per `delegation.md`, since this is a known-target lookup) confirming the one fact is the cheap way to do it without spending main-thread turns.
- Where memory conflicts with what you observe live, MUST surface the discrepancy to the user rather than quietly overriding either side, per `verify-before-acting.md`.
- Another agent session you can message is a remote source too: MUST NOT message one for anything memory, the repo, or your own tools can answer.
- Public web search MUST have one of: the user's explicit direction, memory already recording the web as the right source for this, or the user naming the web when you asked. MUST NOT default to it otherwise.
- When delegating a lookup to a subagent (per `delegation.md`), MUST resolve the source yourself first via the steps above - memory, then a known target, then asking the user if neither applies - before spawning anything. A delegate SHOULD receive an already-resolved source in its spawn prompt, never an open question you have not resolved yourself.
